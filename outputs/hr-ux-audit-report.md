# 克雷迅人力管理系統 UIUX 與操作流程改善建議

## 這次檢視的範圍

本次依目前專案程式碼檢視 `/hr/login`、管理者工作區、會員工作區，以及案件、文件、體檢訓練、待辦、需求單與聊天室的主要流程。這是啟發式與流程檢查，不等同於真實使用者測試；因此下列建議應再用管理者、台灣仲介業務、菲律賓仲介 Staff、雇主與工人各自完成任務測試來驗證。

## 先講結論

系統已經具備相當完整的業務骨架：管理端有案件、文件審核、體檢與訓練、待辦、雇主、工作者、仲介、會員與聊天室；會員端也依角色限制資料，並提供文件、赴台程序與媒合需求。這些是很好的基礎。

目前最大的 UX 風險不是缺少功能，而是**流程被切散，狀態與下一步不夠集中**。管理端同時有「案件階段」「文件狀態」「待辦狀態」「申請程序」四套進度語言；會員端則用五個分頁承載不同角色的資料。使用者很可能看得到資料，卻不確定現在最該做什麼、做完後會影響哪個階段、是否需要回到別的頁面。

建議先做三件事：

1. 把「案件」改成所有角色的共同工作主軸，讓文件、待辦、體檢訓練、申請程序與活動紀錄都能從案件詳情完成。
2. 讓每個角色登入後先看到「我的待辦／需要我處理」而不是單純的資料入口。
3. 統一狀態、錯誤、儲存成功與下一步提示，讓系統持續告訴使用者目前狀態與可採取的行動。這符合 Nielsen Norman Group 提出的「系統狀態可見」「符合使用者語言」「錯誤預防」與「協助使用者從錯誤復原」原則。[1]

## 優先級 P0：應優先改善的流程問題

### 1. 以案件為中心重組資訊架構

目前管理端的側邊導覽把「案件管理」「文件收件與審核」「體檢與訓練」「工作待辦」拆成四個入口；但案件抽屜內又放了工作待辦與案件活動。這會造成同一個工作被分成不同視角：使用者在案件頁看到案件，在文件頁處理文件，在待辦頁更新待辦，卻不容易知道這些動作如何共同推進案件。

建議把管理端主導覽改成：

- 儀表板
- 我的待辦
- 案件
- 需求單／媒合
- 人員與組織
- 文件中心
- 聊天與通知
- 報表或活動紀錄

進入某一案件後，使用一個固定的案件工作區，內含：

- 案件摘要：工作者、雇主、負責業務、案件狀態、目前階段
- 進度時間軸：需求受理 → 媒合 → 文件 → 體檢／訓練 → 申請 → 後續安排 → 完成
- 待辦：只顯示這個案件的未完成工作
- 文件：待收件、待審、退回、已核准
- 體檢與訓練：日期、負責人、完成度
- 活動紀錄：誰在何時做了什麼

目前的七段 `STAGES` 已經可以作為時間軸資料來源，不必另造一套流程模型。重點是把目前分散的資料呈現到同一個案件上下文中，而不是只在案件抽屜裡再堆更多內容。

### 2. 儀表板要從「統計卡片」改成「今日工作佇列」

現在首頁的五張卡片是進行中案件、待審文件、待處理工作、雇主／客戶與工作者，並有最近更新案件和需要留意區塊。這對總覽有用，但對每天要處理案件的人，第一個問題通常是「我現在要做什麼？」而不是「系統共有幾筆資料？」

建議首頁順序改為：

1. 今日逾期與今天到期
2. 待我審核的文件
3. 待我補資料或指派的案件
4. 最近變更的案件
5. 最後才放總量統計

每一列提醒都應可直接進入目標案件或文件。現在「需要留意」中的項目是一般 `div` 呈現，沒有直接操作入口；建議改成可聚焦、可點擊的按鈕或連結，並顯示「逾期幾天」「下一步」「負責人」。系統應在使用者完成操作後立即回饋結果，這正是「Visibility of System Status」的核心要求。[1]

### 3. 把「案件階段」與「狀態」的責任邊界說清楚

目前案件同時有案件階段與案件狀態。文件又有未收件、待審、核准、退回；程序還有開始日與完成日。這些欄位本身合理，但介面要回答三個問題：

- 目前案件在哪一個階段？
- 為什麼會在這個階段？
- 我現在可以做的下一步是什麼？

建議每個案件在頁首固定顯示：

> 目前階段：文件處理｜整體狀態：進行中｜下一步：審核 2 份待審文件

並讓系統以規則計算「下一步」，例如必要文件全部核准後，才顯示「可安排體檢與訓練」。不要只顯示狀態標籤，否則使用者仍需要自己推理。

### 4. 長表單與履歷編輯需要分段、保存草稿與進度

管理者新增案件、工作者、會員、文件要求與仲介的表單主要以 modal 承載；工作者履歷還包含照片、語言、工作經驗與多個欄位。對短資料 modal 很適合，但不適合承載長履歷或需要反覆查資料的作業。

建議：

- 案件新增分為「基本資料」「工作條件」「負責人與備註」三段。
- 工作者履歷改成全頁或大型工作區，左側顯示章節與完成度。
- 顯示「已完成 3／6 節」「最後儲存時間」。
- 支援儲存草稿，不要要求使用者一次完成全部資料。
- 依角色與職類只顯示相關欄位；不相關欄位應被條件式隱藏。

GOV.UK 的表單指南建議先確認每一題為何需要，再依常見情境排序，並將表單拆成讓使用者一次聚焦一件事的步驟；這有助於行動裝置使用與錯誤恢復。[3]

## 優先級 P1：可明顯降低操作成本的 UI 改善

### 5. 用「篩選器」取代只靠自由文字搜尋

目前案件、雇主、工作者與待辦主要透過自由文字搜尋。實際工作常需要的條件是：案件階段、狀態、負責業務、仲介、文件狀態、是否逾期、職類與日期範圍。

建議在搜尋框旁加入可收合的篩選器，並支援篩選條件顯示為 chip：

- 案件：階段、案件狀態、負責業務、仲介、逾期
- 文件：未收件、待審、退回、已核准、不適用
- 待辦：負責人、分類、期限、狀態
- 需求單：媒合中、等待仲介、待面試、已錄用、已取消

同時保留搜尋字串，並提供「清除全部篩選」。這會比讓使用者記住要用姓名、案件編號或職類搜尋更符合「recognition rather than recall」原則。[1]

### 6. 案件清單的整列點擊要改成明確操作

目前案件表格的 `<tr>` 透過 `onClick` 開啟案件，但表格列本身不是鍵盤可操作元件，也沒有可聚焦的明確連結。滑鼠使用者可能理解，鍵盤使用者或使用輔助技術者則可能無法一致操作。

建議：

- 案件編號使用真正的 `<button>` 或 `<a>`。
- 在操作欄放「查看案件」按鈕。
- 不要只依賴整列 hover 或滑鼠點擊。
- 所有互動元素提供可見的 `:focus-visible` 樣式。

WCAG 2.2 要求鍵盤操作可完成頁面功能，並要求焦點指示清楚可見；也把點擊目標大小列為 AA 成功準則。[2]

### 7. Modal 與 drawer 要補齊鍵盤與回復行為

目前多個對話框已標示 `role="dialog"` 與 `aria-modal="true"`，這是好的開始；但程式碼中看不到一致的 Escape 關閉、焦點移入 dialog、關閉後焦點回到原觸發按鈕，以及焦點限制在 dialog 內的實作。

建議所有 modal／drawer 共用一個元件，統一處理：

- 開啟時把焦點放到標題、第一個欄位或關閉按鈕。
- Escape 關閉。
- Tab 不離開 dialog。
- 關閉後回到觸發按鈕。
- 有未保存變更時，關閉前顯示「放棄變更／繼續編輯」。
- 寬度與高度在手機上不造成內容被遮住。

### 8. 文件審核不要使用瀏覽器 `prompt`

文件退回目前使用 `window.prompt` 請使用者輸入補件原因。這個方式不利於說明欄位用途、保留輸入內容、鍵盤與手機操作，也無法在畫面上明確標示這個原因會被誰看到。

建議改成「退回補件」dialog：

- 標題：退回文件並要求補件
- 顯示案件、工作者、文件名稱
- 必填欄位：補件原因
- 可選常用原因：檔案模糊、資料不完整、格式錯誤、文件已過期
- 顯示「工作者會看到這段說明」
- 確認按鈕：退回並通知

錯誤或驗證訊息要直接說明發生什麼事以及如何修正，並且保留使用者已輸入的內容；GOV.UK 的錯誤訊息指南也建議錯誤要靠近對應欄位，並在頁面上方提供錯誤摘要。[4]

### 9. 儲存後的結果要說清楚，不要只依賴短暫訊息

程式有 `message` 與 `role="alert"`，這表示已有回饋機制。不過對高風險操作，例如核准文件、錄用並建立正式案件、停用工作者、刪除需求單，建議把回饋做成可確認的結果：

> 文件已核准。案件 K-2026-001 已進入「體檢與訓練」。下一步：安排體檢。

若資料庫儲存失敗，要顯示：

> 文件尚未上傳。檔案超過 10 MB，請選擇較小的 PDF、JPG 或 PNG。原本表單內容已保留。

不要只顯示「儲存失敗」或技術錯誤。Nielsen Norman Group 建議錯誤訊息使用一般使用者看得懂的語言，明確指出問題，並提供立即可採取的解法。[1]

## 優先級 P1：角色導向的操作流程建議

### 管理者／主管

登入後先看到「待我處理」：待審文件、逾期案件、待分派業務、待審會員。點擊一筆提醒後直接進入案件工作區，完成操作後返回原佇列，避免來回找頁面。

### 台灣仲介業務

登入後主畫面應以「我的雇主」「我的案件」「雇主需求單」「待面試／待錄用」為主。若目前使用的是「仲介／雇主資料」分頁，建議把它拆成較符合任務的「雇主」與「需求單」，不要讓使用者先理解資料模型再找工作。

### 菲律賓仲介 Staff

收到工作需求後，流程應固定成：查看需求條件 → 查看可推薦工作者 → 查看履歷 → 推薦 → 等待面試結果。現在可推薦人選、需求資訊與推薦說明已存在，但建議加入明確的步驟標籤與送出後的狀態，例如「已推薦，等待雇主安排面試」。

### 雇主

雇主最重要的流程是：建立需求 → 查看符合條件的工作者 → 查看履歷 → 挑選 → 安排面試 → 錄用。建議把這六步做成需求單內的狀態時間軸，並將「錄用」的後果寫在按鈕附近，因為目前錄用會建立正式申辦案件，屬於高影響操作。

### 工人

工人應以「我的案件進度」「待補文件」「文件上傳」「赴台流程」為首頁，而不是先看到大量資料分頁。對工人來說，最重要的資訊是：還缺什麼、誰在處理、何時完成、下一步要由誰做。

## 優先級 P2：視覺與內容一致性

### 10. 統一產品命名與角色語言

目前同一產品中同時出現「克雷迅人力管理」「克雷迅人力仲介管理系統」「KOLECION HR」；角色文字也有工人、工作者、業務、Broker、Staff、仲介等不同稱呼。這些稱呼可能符合不同對象，但要建立一份詞彙表，並在每個角色的介面只使用該角色理解的名稱。

例如：

- 系統內部資料模型可用「worker」，使用者介面統一用「工作者」或「工人」，不要在同一個操作流程混用。
- 台灣仲介會員固定顯示「業務」，菲律賓仲介會員固定顯示「Staff」。
- 「案件」「需求單」「申請程序」要在說明文字中定義彼此關係。

這符合 Nielsen Norman Group 所說的「match between system and real world」：介面要使用使用者熟悉的語言，而不是內部資料模型的術語。[1]

### 11. 提高小字、狀態與表格的可讀性

管理端 CSS 大量使用 10–12px 的輔助文字與表格文字。這能讓資訊密度提高，但在人力案件這種需要長時間閱讀的系統，容易造成掃讀疲勞，尤其是文件名稱、案件備註與活動紀錄。

建議：

- 主要表格文字至少維持 13–14px。
- 輔助說明不要低於 12px。
- 不要只用紅、黃、綠表達狀態，搭配文字與圖示。
- 表格欄位可依角色隱藏，將不常用欄位放進詳情。
- 在手機上優先用卡片顯示案件摘要，不要讓使用者橫向拖曳才能理解一筆案件。

### 12. 登入頁增加「註冊與登入的差異說明」

登入頁已支援 LINE、Google 與 Email／密碼，也有註冊模式，這是完整的入口；但註冊流程涉及「使用 LINE 確認身分 → 選擇會員類型 → 選擇所屬仲介 → 等待審核」，建議在註冊頁直接用 3 步驟說明，並清楚告知「送出後不會立即取得案件資料，需等待管理者核准」。目前已有相關說明，可再提升成視覺化流程，降低使用者誤以為註冊後立即完成的風險。

## 建議的第一版改版範圍

若要控制開發量，我建議第一階段只做以下 6 項：

1. 新增「我的待辦」頁，並讓儀表板提醒列可直接開啟案件。
2. 將案件詳情抽屜升級為案件工作區，集中顯示進度、文件、待辦與下一步。
3. 文件退回改用自製 dialog，取代 `window.prompt`。
4. 案件與文件清單增加狀態、逾期、負責人篩選器。
5. 案件編號改為真正可鍵盤操作的連結或按鈕，補上 modal 的 Escape 與焦點管理。
6. 統一狀態文案與儲存後訊息，明確顯示「完成了什麼、下一步是什麼」。

## 驗收時應測試的任務

改版後至少請五類角色各自完成一個任務：

- 管理者：找出所有待審文件，退回一份並確認申請人看得到補件原因。
- 台灣業務：從雇主需求單找到待面試人選，完成錄用並找到新建案件。
- 菲律賓 Staff：收到需求後推薦一名工作者，確認狀態變成已推薦。
- 雇主：建立需求、查看履歷、挑選人選、安排面試。
- 工人：登入後找到待補文件、上傳新版本、確認文件進入待審核。

每個任務記錄四個指標：是否成功、完成時間、卡住的位置、是否需要他人解釋。尤其注意「找不到下一步」「不知道是否儲存成功」「不知道資料會被誰看到」這三類問題。
